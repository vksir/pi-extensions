# /token 用滚动时间窗聚合 turn 明细

`/token` 原来按会话展示平均首字与平均速率。会话可以横跨几小时甚至几天，会话内的平均速率会被不同时间、不同模型、不同任务混在一起，用户看到的数字没有解释力。用户真正关心的是「最近一段时间，这个模型/厂商跑得多快」，并明确只需要过去 1 小时（必要时 3 小时），不需要按天、按会话拆分。

SQLite 的 `turn` 表从引入起就按响应逐行记录时间、模型、输出 token、耗时与首字，已经足够回答这个问题。原来的 `day_model` / `session` 是面向日汇总与会话汇总的物化表，对滚动窗口反而不好用：按天汇总无法表示任意小时边界，按会话汇总把时间维度丢了。

## 决策

- **默认过去 1 小时**：`/token` 不带参数时汇总最近 1 小时；支持 `3h`、`30m`、`1d`、`all` 等显式时间窗。默认值只在这里定义一次。
- **直接聚合 `turn` 明细**：查询条件只有 `at >= 窗口起点`，按 `provider + model` 分组。不建按小时/按分钟的汇总表：滚动窗口的边界不固定，预聚合要么失真，要么需要复杂的补算。
- **所有会话、所有进程一视同仁**：不再有「当前会话」区块。多个 pi 进程共用同一个库，`turn` 里的每一行都参与聚合，会话 id 只作为明细来源保留。
- **只展示两个指标**：每行给 `Turns`（含没有计时样本的响应）、`TTFT`（测到首字的样本均值）、`Rate`（有耗时响应的输出之和 ÷ 耗时之和，token/秒）。`Rate` 按 token 加权，耗时取完整请求时间（含首字等待），与 footer 的口径一致。最后一行 `All models` 是所有模型的合计。
- **schema v2 迁移**：打开旧库时把 `day_model` / `session` 改名为 `archive_day_model` / `archive_session`，数据保留但不再写入、也不再读取；删除 v1 的 `turn_session` 索引；版本号写入 `meta.schema_version`。迁移只做一次，多个进程同时打开时靠 `BEGIN IMMEDIATE` 排队。
- **删除旧 JSON 导入**：`token-stats-legacy.ts` 是上一版明确标注「下个版本删除」的临时代码。v2 之后按小时统计只依赖 `turn`，旧 JSON 没有逐轮时间与首字，无法补出可用样本；已导入的数据留在归档表里。

## 被否决的选项

- **保留按会话平均，再加时间窗**：两套口径同时存在会让用户不断比较两个不同分母的数字；用户已经明确说会话平均没有意义。
- **用 `day_model` 算「过去 1 小时」**：只能按自然日切，凌晨与跨日窗口都会错。
- **新建 `hour_model` 汇总表**：1 小时窗口可以按整点聚合，但用户可能查 `30m`，且窗口起点随时间滑动；按小时间隔物化要么多算要么少算，最终仍要回查明细。
- **继续写 `day_model` / `session` 只为了兼容**：写放大、代码分叉，且没有任何读取方。归档比继续双写更诚实。
- **把速率改成「输出 ÷（耗时 − 首字）」**：生成速率看起来更高，但与 footer 的既有口径不一致，也让 `TTFT` 与 `Rate` 两个数字的分母难以对照。统一用完整请求时间，口径写在表尾注释里。

## 后果

- 时间窗统计只覆盖 SQLite 里有 `turn` 明细的响应。旧 JSON 的日/会话汇总留在归档表，不会出现在 `/token`；这是可以接受的，因为它们的粒度本来就不支持小时窗口。
- 只装过旧 JSON、从未建过 SQLite 库的用户，升级后不会自动导入旧数据；`token-stats.json` 原文件仍在 agent dir 下，需要时可手工查。
- `turn` 表一轮一行，数据库随使用线性增长；`turn_at` 索引让窗口查询只扫最近一段。清理策略不在本 ADR 范围。
- footer 的首字/速率仍取内存里的最近一次响应，与 `/token` 的时间窗报告是两条独立路径；两者共用同一套格式化函数，口径一致。
