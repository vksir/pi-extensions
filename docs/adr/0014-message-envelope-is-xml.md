# 消息信封：<agent_message> + <content> + <note> + type

## 背景

在 [ADR-0012](0012-agent-replies-are-sends.md) 之后，消息是「`<agent id "name">` 首行 + 正文 + 末尾 `<reply>` 一块」：三段平铺，没有共同的根，模型要自己拼「谁发的、这算不算一条完整消息」。同时「等回信」台账无法分辨对方发来的是一条新活还是一条回信，只能收到任何消息就销账，导致「发两条、只回一条」被当成已回。

## 决策

- 单一根元素：`<agent_message from="…" name="…" type="task|reply|notice">`。
- 正文放进 `<content>`，统一缩进 4 格；解析时剥回，正文里的缩进不变形。
- `task` 带 `<note>`：`Your output is not returned automatically. Use agent_job send with type="reply" to reply.`；`reply` 与 `notice` 不带。
- `</content>` 与 `<note>` 之间只换行、不空行；`<note>` 的文字另起一行。
- 解析不依赖 XML 库：匹配根元素的 `from` / `name` / `type`，再取 `<content>` 与 `</content>` 之间的正文；其余忽略。
- `agent_job send` 增加 `type` 参数（`task` 默认 / `reply`），拉起子 agent 恒为 `task`，退出通知恒为 `notice`。
- 台账按类型记账：出站一条 +1；入站 `reply` 一条 −1；入站 `task` 不销账。目标子树退出且账还没清，才发 `notice`。

## 被否决的选项

- **自闭合的 `<reply …/>`**：没有正文位置，指令只能塞进属性，模型读起来像数据而不是要求。
- **不做根元素、只把首行改成属性**：仍是「首行 + 散装块」，模型没有整体边界。
- **用 `<body>` 而不是 `<content>`**：同义，多一层标签没有收益。
- **正文严格按 XML 缩进**：会把代码块整体右移；现在的做法是只在收发两端加减 4 格。
- **把 `<note>` 放在首行或系统守则里**：实测首行标记与守则都不足以让模型回信；放在消息结尾更有效。

## 后果

- 每条消息多约 40 字符（根元素 + `<content>` + `<note>`）。
- 旧格式消息一律不认，升级时所有 agent 一起重启。
- 台账能区分「新活」与「回信」：同一目标发几条就记几笔，回一条销一笔；对方发来新活不会把「还没回我」误判成已经回过。
- 正文里出现 `</content>` 会在那里截断；正常写作不会碰到，这是已知边界。
- `type` 由发送方声明：发送方把回信写成 `task`，接收方的台账就不会销账，可能多一条「退出了没回信」。宁可多报，不漏报。
