# agent 之间只有 send：回信交给模型，扩展不代发

## 背景

ADR-0011 把回信挂在扩展上：收工时把本轮最后一段回答自动发给「派活人」，`result` 轮次不回发。两层链路就断了 —— A 派活给 B，B 拉起 C 后收工，A 收到「已派给 C」；C 的结果回到 B 时这一轮是 `result` 轮次，按规则不回发，A 再也拿不到最终结果。

先试过的补法（现状被否决）：在 B 的内存里记一张 relay 表（子 id → 派活人），子结果到达时把原来的派活人接成这一轮的回发收件人。它能补上第二跳，但「谁在等谁」又回到了扩展内存里，与「主 agent 自己掌握对话」的方向相反；而且要另外给「子进程崩溃 / 被 stop，结果永不到达」补兜底。

结论：回信本来就该是 agent 的判断，不是某个窗口里必须发生的事件。给它一个动作，让它自己发。

## 决策

- `agent_job` 的 `ask` 改名 `send`，语义不变：不检查对方状态，忙不忙由对方的 pi 按 steering 模式处理。**派活与回信是同一个动作**，模型自己决定发给谁、发几次。
- 删除收工自动回发。`agent_settled` 一条消息也不发；`lastAnswer`、`agent_end` 钩子、结果截断与全文落地、死信箱记录一并删除。
- 删除 `result` 首行位；消息格式后来统一成 `<agent_message>` + `<content>` + `<note>` + `type`（[ADR-0014](0014-message-envelope-is-xml.md)）。`task` 消息带 `<note>`：输出不会自动回传、要回就用 `agent_job send with type="reply"`。它只陈述事实，不要求回信；回不回仍由模型决定。
- 删除由扩展代发的三类通知：崩溃 / 退出（「没来得及回答」「你那条没做」）、UI 弹窗 blocked、中止的 `Run aborted.`。要知道对方状态就 `agent_job list`。
- 保留：`stop` 先礼后兵、空闲销毁。
- 补一条兜底：本进程发过消息的目标，收到 `type="reply"` 才销账；目标整棵子树都退出了仍没回信，就给本地 agent 发一条 `type="notice"` 消息。这是扩展唯一自己发的消息，也是「全权交给模型」下唯一会静默丢答案的地方的补丁。
- 提示词：`send` 的动作语义写在工具描述里；「回信也用 send」只写在 `agent_job` 的守则里，两处不重复。

## 被否决的选项

- **relay 记账 + 回发收件人 fan-out**：子 agent 的 result 到达时接回原来的派活人。能修好两跳链路，但把「谁在等谁」重新放进扩展内存，还给崩溃补了新的兜底需求。
- **保留自动回发，只在模型自己 send 过时跳过**：能避免重复，但等于留两套回信路径，行为取决于模型这一轮有没有 send 过。
- **子 agent 直接回给最初的派活人**：B 还要整合 C 的结论，绕过 B 会丢信息；C 也只认识父 id。
- **让 B 阻塞等 C**：违背「拉起不等结果」，一轮不结束就没法空闲销毁。
- **多给一条 `reply` 动作**：与 `send` 完全重合，模型多一层选择就多一层选错。

## 后果

- 模型忘了回信，对方就永远等下去 —— 没有兜底。确认状态只能 `agent_job list`，人看 `/agent list`。
- 一次派活可能收到多条消息（中间进展 + 最终结果），也可能一条都没有：收件方必须把 agent 消息当消息，不能假设它与某次请求一一对应。
- 结果不再截断：长回答由模型自己控制，扩展不再落 `pi-herdr-agent-*.log`。
- 崩溃、被 `stop`、卡在弹窗都不再有通知；`session_shutdown` 只做自己的收尾与子终端清理。唯一的例外是上面那条「退出了没回信」，它由发消息的一方观察子树得到，不依赖对方自己上报。
- 排队与发起人后来也删了（[ADR-0013](0013-inbound-messages-are-inserted-not-queued.md)）：忙时消息直接交给 pi 插进当前轮。
- 回信提示只活在消息里（`task` 的 `<note>` 元素），不再是系统守则：模型不看消息就不会回。首行不说明「你是子 agent」。
