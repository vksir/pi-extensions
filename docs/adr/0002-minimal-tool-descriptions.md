# 工具描述只放参数语义，使用指令移出常驻上下文

pi 会把每个工具的 `description` 与参数 JSON Schema（含每个字段的 `description`）在**每次请求**里完整序列化出去，而且 pi 没有 Claude Code 的 `shouldDefer` / ToolSearch 机制可以延后加载（那是 Anthropic 服务端的 beta 协议能力）。因此工具描述写多长，就永久占多少上下文。我们据此确立分层：**工具只回答「这是什么、参数是什么」，其余信息一律移到非常驻载体**——扩展命令（0 常驻）、skill 正文（仅 `description` 常驻，正文按需加载）、工具返回文本（调用后付费）。

pi-cron 是这条准则的第一个实例：工具 schema 常驻 768 字符（≈192 tokens），人工入口是一个扩展命令 `/cron`（0 常驻，间隔由代码解析，完全不经过 LLM）。把 CC 那段 3,394 字符的创建提示词放进工具描述的写法约 4,162 字符（≈1,041 tokens），每轮差约 850 tokens；「创建后立即执行一次」这类行为约定则写在工具返回文本里，一次调用付一次。

中途曾走第三条路：一个 20 行的 skill（`/skill:cron`）承载「间隔→cron」的转换规则，并标 `disable-model-invocation: true` 使其只服务人工调用。它最终被**删除**——因为 `/cron` 命令已经覆盖创建/查看/删除且完全确定性，skill 只剩「同功能里质量更差的重复入口」，还让同一套换算规则在代码与文档里各存一份。

## 被否决的选项

- **照搬 Claude Code 的富工具描述**：CC 的 `CronCreate` 提示词有 3,394 字符，它敢这么做是因为 `shouldDefer: true` 把 schema 藏进了 ToolSearch。pi 没有这个机制，照搬就是把 CC 的解法连同它不存在的前提一起搬过来。
- **让 skill 保持模型可见**：模型能自发排期，但 skill 的 `description` 会常驻；而且模型仍然需要一份「间隔→cron」的规则，与命令里的代码实现重复。
- **让 skill 只服务人工调用（`disable-model-invocation: true`）**：常驻降到 0，但同一套规则两处维护；一旦又加了确定性的人工命令，它就彻底冗余。
- **运行时按需注册工具**：pi 支持在命令处理器里 `registerTool` 且立刻生效，理论上可以「用到才注册」。但工具名必须先存在于模型视野里才可能被调用——先有鸡还是先有蛋。

## 后果

- 新增工具时应默认问一句：这条信息是模型每次都用得上的，还是只在动手时才需要的？只把前者留在工具描述里。
- 模型能否**自发**使用某个能力，取决于是否有可见的 skill `description` 或工具描述；把信息藏进 skill 正文会同时藏掉「模型想起来要用它」这件事。这是本准则的真正代价，取舍时要显式确认。
- pi-cron 的取舍结果：模型侧发现完全交给工具描述；人工侧由 `/cron` 命令承担，**规则只存在于代码里一处**。代价是模型主动发起时不再有「默认间隔 10m」与「`Ns` 取整到分钟」这两条约定（它们只服务命令路径）；而「创建后立即执行一次」因为在工具返回文本里也写了一份，所以不受影响。
- **同一套规则不要同时存在于代码与提示词里**。两条入口可以共用同一个实现（pi-cron 的 `createJob()` 同时服务命令与工具），但不该共用同一个「以自然语言重述的规则」——那种重复没有编译器保护。
- 工具返回文本是常被忽略的第三块载体：它既不是常驻，也不像 skill 那样需要一轮读取，适合承载「接下来该做什么」的指令。
- **扩展命令是 0 常驻的人工入口**。凡是「用户主动发起」的动作，优先考虑命令而非让模型解析——命令的解析是确定性的，且不消耗任何常驻上下文。
