# 忙时收到的消息直接插入，不再排队

## 背景

[ADR-0011](0011-agent-dispatch-owner-and-queue.md) 的派发规则是：忙时非发起人发来的消息被扩展吞掉，按发送方聚合成一条，等收工后再逐条起轮。它解决了「忙是错误」，但代价是：

- 发送方以为消息已经送达，实际要等整个当前轮结束；等待期间没有任何模型可见的反馈。
- TUI 每来一条就记一行 `⏸ … queued`，同一发送方的多条看起来像多条队列，实际早已合并、位置不变。
- 队列只在进程内存里，退出即丢；空闲销毁还要专门绕开非空队列。
- 谁该读、什么时候读，全由扩展判断；而现在已经把回信交给模型自己 `send`，扩展没有理由再替它决定。

## 决策

- 删除排队：`input` 里不再吞消息、不再按发送方聚合、不再在收工时起队首。所有 agent 消息原样交给 pi（`transform`），忙不忙、插不插队由 pi 的 steering / follow-up 模式决定。
- 删除发起人（`owner`）与 `busy` / `settling` 状态：它们只为旧的分发规则服务。
- 删除排队的 TUI 记录（`⏸ … queued` 与 `+1 merged`）。
- 空闲销毁的「安静」判定保留，但不再检查队列（没有队列了）。
- 「没回信」通知保留：它按目标 id 记账，与消息是否排队无关；目标整棵子树都退出仍没回信就通知本地 agent。

## 被否决的选项

- **保留队列、只修 UI**：治标；消息仍被延迟与合并，模型仍然看不到等待。
- **保留「发起人」的插话特权**：同一件事会出现两套规则（扩展一套、pi 的 steering 一套），最终以 pi 为准反而更简单。
- **让扩展自己按 steering 模式实现插入**：pi 已经做了，重写一遍只会产生分叉。

## 后果

- 忙时消息立刻进入当前轮（`steeringMode=all` 时），可能与正在进行的任务交错；`one-at-a-time` 下会被 pi 逐条延后，扩展在启动时提醒改成 `all`。
- 不再有按发送方的合并与顺序保证：同一发送方连发三条，就是三轮新的输入。
- 消息不再有「稍后起轮」的语义：空闲时收到就起一轮，忙时插入当前轮。
- 队列的 TUI 行消失；「等回信」通知仍会出现，且与插入逻辑互不影响（通知按目标记账，只看它整棵子树是否退出）。
